# 모바일 OTP — Zero-Transmission TOTP 체험 스튜디오 (`26-w11-mobile-otp`)

> RFC 6238 표준에 기반하여 브라우저 내부에서만 암호학적 연산을 수행하고, 실제 스마트폰 Authenticator 앱과 100% 실시간 동기화되는 **단일 화면 양방향 비교 체험 스튜디오**입니다.

---

## 🌟 프로젝트 소개: 앱의 컨셉과 화면 구성

복잡한 페이지 이동이나 백엔드 서버 없이, 한눈에 TOTP(RFC 6238)의 원리를 직관적으로 이해하고 테스트할 수 있도록 **단일 화면 좌우 분할 비교 스튜디오**로 기획했습니다.

* **[좌측 패널] 서비스 서버 (인증 제공자 - ServerPanel):**
  * **CSPRNG 비밀 키 발급:** 앱 접속 즉시 160-bit 암호학적 안전 난수 기반 Base32 비밀 키 자동 생성 및 `[새 비밀 키 발급]` 버튼 제공
  * **비밀 키 보호 및 편의:** 32자리 비밀 키 마스킹 토글(`••••••••` / 원문 보기) 및 클립보드 원클릭 복사
  * **표준 QR 코드 등록:** `QRCodeSVG`를 사용한 표준 `otpauth://totp/...` QR 코드 렌더링 (Google/Microsoft Authenticator 스캔 지원)
  * **6자리 코드 검증:** 사용자 입력 코드 판정 및 직관적인 성공/실패 시각적 배너 피드백 제공
* **[우측 패널] 인증기 앱 시뮬레이터 (스마트폰 역할 - ClientPanel):**
  * **실시간 6자리 OTP 계산:** 30초 주기마다 Web Crypto API로 HMAC-SHA1 연산을 수행해 6자리 코드 자동 갱신
  * **정밀 카운트다운 타이머:** 250ms 주기 부드러운 프로그레스 게이지 바 및 5초 이하 만료 임박 시 시각적 경고(Pulse & Red Color) 효과
  * **연동 지원:** 우측 시뮬레이터 번호를 좌측 검증창으로 즉시 채워주는 테스트 바로가기 링크 제공

## 🚀 나의 AI 기획·구현 과정

### 1. 선택한 AI 협업 방식
* **Gemini 웹 기반의 밀도 높은 사전 기획:**
  무작정 코드를 치기 전에 Gemini 웹을 통해 5가지 핵심 기획 질문, 4가지 필수 기준, 2가지 필수 보안 원칙을 단단히 정의하고 완전한 **최종 PRD**를 먼저 확정했습니다.
* **Antigravity IDE의 단계별 Implementation Plan & 단위 커밋 워크플로우:**
  확정된 PRD를 기반으로 Antigravity IDE에서 `[1단계 암호화 순수 모듈] -> [2단계 양방향 UI 컴포넌트 & 상태 연동] -> [3단계 검증 및 보안 점검]` 순으로 명확한 마일스톤을 세워 실행했습니다. 작은 기능 단위마다 GEMINI.md 규칙에 맞춘 Git 세이브포인트를 남겨 안정적인 개발 흐름을 유지했습니다.

### 2. 시행착오와 스마트폰 앱 연동 디버깅 경험 (성공의 쾌감!)
가장 신경 썼던 부분은 **"스마트폰의 Google/Microsoft Authenticator 앱과 브라우저 화면의 6자리 숫자가 1초의 오차도 없이 100% 일치할 수 있는가?"**였습니다.

* **발생할 수 있었던 복병 사전 차단:**
  * Base32 문자열의 불필요한 패딩(`=`)이나 공백, 소문자 입력으로 인한 바이트 배열 왜곡 방지
  * JavaScript의 32비트 비트 연산 한계로 인한 타임 카운터 오버플로우 문제
* **해결 및 검증:**
  * 표준 RFC 4648 Base32 인코더/디코더를 정규화하여 작성했습니다.
  * 카운터 버퍼 구성 시 일반 배열 대신 반드시 `DataView.prototype.setBigUint64(0, BigInt(counter), false)`를 적용해 **8바이트 Big-Endian** 규격을 완벽하게 충족시켰습니다.
  * 구현 직후 RFC 6238 공식 표준 테스트 벡터 4건(`Time 59s -> 287082`, `Time 1111111109s -> 081804` 등)을 사전에 검증하여 100% Pass를 확인했습니다.
* **스마트폰 첫 실전 스캔의 순간:**
  화면에 생성된 QR 코드를 스마트폰 Google Authenticator 앱으로 스캔하자마자, **스마트폰의 6자리 번호와 우측 시뮬레이터 화면의 번호가 동시에 깜빡이며 똑같은 숫자로 변하는 순간** 엄청난 성취감을 느꼈습니다!

## 🛡️ TOTP 원리 및 보안 점검 (사이버보안과 체크포인트)

### 1. `Math.random()` 대신 `crypto.getRandomValues()`를 사용하는 이유
* `Math.random()`은 의사 난수 생성기(PRNG)로서 내부 알고리즘이 예측 가능하여, 암호학적 공격자가 이전 생성 값들을 관찰하면 향후 생성될 비밀 키의 시드(Seed)를 역추적할 수 있습니다.
* 반면 `window.crypto.getRandomValues()`는 운영체제 하드웨어 엔트로피를 사용하는 **암호학적으로 안전한 의사 난수 생성기(CSPRNG)**입니다. 이를 통해 160-bit(20바이트)의 예측 불가능한 안전한 비밀 키를 생성하여 키 추측 및 무차별 대입 공격을 원천 차단했습니다.

### 2. Web Crypto API (`crypto.subtle`) 기반 Zero-Transmission의 보안 이점
* **공격 표면(Attack Surface)의 원천 제거:**
  비밀 키 생성 및 HMAC-SHA1 서명 연산이 외부 인증 서버나 서드파티 API를 거치지 않고 오직 브라우저 샌드박스 내부(`crypto.subtle`)에서만 처리됩니다. 네트워크를 전혀 타지 않으므로 전송 구간 도청(Man-In-The-Middle), 패킷 탈취, 서버 메모리 유출 위험이 물리적으로 존재하지 않습니다.
* **개발자 도구 Network 탭 점검 결과:**
  새 비밀 키 발급, QR 생성, 실시간 OTP 계산 및 6자리 검증의 전체 라이프사이클 동안 브라우저 개발자 도구(F12) Network 탭을 모니터링한 결과, **외부 HTTP/WebSocket 요청이 정확히 0건(Zero-Transmission)**임을 확인했습니다.

### 3. 스마트폰 Authenticator 앱과의 일치 여부
* Google Authenticator 및 Microsoft Authenticator 모두에서 QR 코드 인식 즉시 정상 등록되었으며, **30초 주기 변경 시마다 스마트폰 앱과 웹 화면의 OTP 코드가 100% 일치**함을 확인했습니다.

## ⚡ 나만의 확장 기능: 시간 오차 허용 (±1 스텝 / ±30초 보정 토글)

실제 사용자 환경에서는 스마트폰과 서버(또는 PC) 간의 시스템 시계가 수 초~수십 초가량 미세하게 어긋나 있을 수 있습니다.
* 복잡도를 가중시키는 불필요한 다중 계정 저장은 걷어내고, 실무 보안 규격에서 가장 필수적인 **±1 스텝(앞뒤 30초) 시간 오차 허용 토글**을 구현했습니다.
* 사용자가 스위치를 켜면 이전 스텝(-30초), 현재 스텝(0초), 다음 스텝(+30초) 총 3개 윈도우를 순회 검증하여 실생활 시계 오차로 인한 인증 실패 스트레스를 깔끔하게 해소했습니다.
* 검증 성공 시 배너를 통해 몇 스텝 오차로 승인되었는지(예: `현재 구간 일치`, `직전 스텝 보정 인정`) 상세한 원인 피드백을 제공합니다.
